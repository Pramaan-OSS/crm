## 1. What is being built

Pramaan is a governed product builder. A non-technical founder describes a product, accepts a brief and a plan, and Pramaan builds it one sprint at a time with proof at every step, in a repository the founder owns. Two further lanes exist: hand off existing code (Lane A) and work in a repository an engineering team owns (Lane B).

The interface is one shell with three glass islands: a top bar, a chat with Pramaan on the left, and a results pane on the right. The chat always holds the one next decision. The results pane holds the job (a list, a form, a document, a plan, a board, a preview).

Users work at a desktop browser. The reviewer's window is 1142×732 CSS px. Every screen must work there with no nested scrollers and nothing clipped. Mobile is not a phase 0 target, but the page must not scroll horizontally at 400px wide (see §12).

## 2. The seven invariants (every screen, every state)

Each invariant has a pass condition. The acceptance script in §13 checks the automatable ones.

| # | Invariant | Pass condition |
|---|---|---|
| I1 | **One thread.** Exactly one element per screen uses the thread colour: the next decision | `document.querySelectorAll('[data-thread]').length === 1`, or `=== 0` when `main[data-thread-none]` is present. Never 2 or more. A disabled control is never thread-coloured |
| I2 | **Two scrollers.** Only the chat messages and the right view scroll | Elements inside `main` with `overflow-y` auto/scroll and `scrollHeight > clientHeight` are exactly `.msgs` and/or `.view`. The top bar, strip, dock and composer never move. A textarea is not a scroller (`overflow: hidden`) |
| I3 | **Always know where you are.** Breadcrumb and tabs agree on the project and stage | `.crumb` has ≥ 1 link on project screens; exactly one `.tab[aria-current="page"]` when a tab is active; a locked tab has a `title` that says when it opens |
| I4 | **The main job owns the space.** The right view's job starts within 140px of the pane top and the pane is ≥ 60% of the width | `.right` width ≥ 0.6 × (`main` width); first job element top ≤ 140px from `.right` top |
| I5 | **Plain words, fixed states.** Seven status pins only, each followed by one plain sentence | Every `.pin` has `data-pin` in {Needs you, Working, Waiting, Done, Paused, Blocked, Locked} and visible text equal to it; every `.pin` inside `.state`, `.dock .status` or `.m-status` is followed by a text node |
| I6 | **Nothing is lost.** Project screens show the last-saved / last-accepted strip | `.strip` is visible on every project screen (not on Projects, New project, Live logs, Lane entry forms) |
| I7 | **The right pane never holds a primary action** | No `[data-thread]` and no `.btn-thread` inside `.right`. Quiet buttons only |

- Headings are serif at weight 400 everywhere. Never 500 or above on a serif.

- Sentence case for every label, button, tab, pin and field label. "Needs you", not "Needs You" or "NEEDS YOU".
- Numbers that line up in columns get `font-variant-numeric: tabular-nums` (`.num`).

## 7. Components

Each component lists: anatomy (the DOM the prototype emits), sizes, states, accessibility, rules. Class names are the prototype's; keep the `data-*` attributes verbatim in the app because the acceptance script reads them.

### 7.1 Top bar `.top`

Anatomy, left to right:
1. `a.wordmark` → Projects. Text "Pramaan" 21px serif plus `<i>` 8px ink dot. `aria-label="Pramaan, all projects"`.
2. `nav.crumb` (`aria-label="Breadcrumb"`): 13px, `--fg-3`, segments separated by `<span class="sep">/</span>` with 8px margins; the leaf is `<b>` in `--fg` weight 500; every non-leaf is a link; the first crumb is always "Projects" → the projects list. Truncates with an ellipsis, never wraps.
3. The request measure tape (§7.3), only on Lane B request detail. On every other screen this cell renders an empty `div` so the grid does not collapse.
4. `.top-actions`: two `a.btn.btn-icon` (Settings → sliders icon, Live logs → terminal icon) each with `aria-label` and `title`, plus `button.avatar` 32px circle, `--inverse` fill, 11px 600 initials, `aria-label="Account: <name>"`.

When the current page is Settings or Live logs its icon button carries `aria-pressed="true"` and renders with `--surface-sunk` fill and `--line` border.

### 7.2 Journey tabs `.tabs` (the single journey)

The tabs are the journey. There is no second journey indicator on founder screens.

Anatomy: `nav.tabs[role=tablist][aria-label="Project views"]` containing one `.tab` per view, then `.spacer`, then an optional `.meta` (right-aligned sentence such as "4 requests · 1 needs you").

Project tabs in order, with icons: Overview (grid), Decisions (chat bubble), Documents (file), Roadmap (route), Build (hammer), Try it (play). Home tabs: Projects (folder), Live logs (terminal). Entry tabs: Projects, then New project (sparkle) / Hand off your code (upload) / Choose your repository (branch). Lane B project tabs: Requests (list), Settings (sliders).

Each `.tab`: 13px 500, padding `8px 12px 14px`, icon 15px before the label, `--fg-3`; hover `--fg`. States via `data-state`:

| State | Rendering | Attributes |
|---|---|---|
| open / upcoming | label only | `a`, `title` = "<Step> has not started yet." when upcoming |
| current page | `--fg`, 2px underline from 12px to 12px inset at the tab bottom | `aria-current="page"` |
| done | green 12px check after the label | `data-state="done"`, check `title="Done"` |
| locked | opacity .5, lock glyph after the label, not a link | `span.tab[data-state="locked"]` with `title` = the reason ("Opens after the plan is approved", "Opens when sprint 1 is ready to try", "Opens when your private copy is ready") |

Derivation: the five journey tabs take their state from the project's real stage (interview, documents, roadmap, build, try it). Steps before the current stage are done, the current is current, later steps are upcoming, and a step whose gate has not been passed is locked. Overview is never locked. The Lane A import case marks Interview done with the tooltip "Interview: you brought a document instead".

### 7.3 Request measure tape `.tape` (Lane B request detail only)

`ol.tape[aria-label="This request"]` with four `.node` pills: Build, Test, Review, Merge. Node: 28px tall, padding 0 12px, 12px 500, pill, glass button surface; connectors are 12px hairlines between nodes. States via `data-state`: `done` (check icon, link), `current` (`--inverse` fill, `aria-current="step"`), `upcoming` and `locked` (dashed `--line` border, `--fg-3`, no fill; locked also `cursor: not-allowed` and lock icon), `blocked` (`--blocked` border and text). Every node has a `title` with its reason; Review's title reports rounds ("Review: 2 rounds").

**Project mark algorithm** (implement exactly; the prototype's `mark()` in `build.mjs` is the reference):

1. Hash the project name with FNV-1a 32-bit: `h = 2166136261; for each UTF-16 code unit c: h ^= c; h = Math.imul(h, 16777619) >>> 0`.
2. Draw a 36×36 viewBox: `rect.t` 36×36, `rx` 10, `--fg` at 6% opacity (the tile).
3. Four cells at origins (2,2), (18,2), (2,18), (18,18), each 16×16. For cell i: `kind = [0,0,1,1,2,3][bits % 6]; bits = floor(bits / 6); rot = (bits % 4) * 90; bits = floor(bits / 4)`, starting with `bits = h`.
4. Cell kinds: 0 = quarter disc (`path.b` `M x y h16 a16 16 0 0 1 -16 16 z`), 1 = quarter arc (`path.s` `M x+2 y+14 a12 12 0 0 1 12 -12`, stroke 2.5, round caps, no fill), 2 = dot (`circle.b` r 3.2 at the cell centre), 3 = empty. Each cell is wrapped in `g` rotated by `rot` about the cell centre.
5. Accept the composition only if at least 3 cells are non-empty, at least 2 distinct kinds are present, and the composition key (`kind+rot` per cell joined by `-`) has not been used by another project in the same list. Otherwise rehash with `hash(name + ':' + tries)` and repeat, up to 128 tries.
6. Colours: `.b` fill `--fg`, `.s` stroke `--fg`, `.t` fill `--fg` at 0.06 opacity. Nothing else. The mark is `aria-hidden="true"`; the project name is the accessible label.

The mark is deterministic per name, so the same project shows the same mark everywhere. Uniqueness is enforced per list render (projects list); a collision between projects on different pages is acceptable.

## 9. Behaviour

- **Thread.** Exactly one `[data-thread]` per rendered screen (I1). When the screen's decision changes (an answer submitted, a draft accepted) the dock re-renders; nothing else on the screen becomes blue.
- **Tabs and locks.** Clicking a locked tab does nothing; its `title` explains. Clicking a done or current tab navigates.
- **Chat.** Messages append at the bottom; the scroller follows the newest message unless the user has scrolled up more than 80px, in which case show a "New reply below" pill (`.m-ctx` style, clickable) instead of forcing the scroll.
- **Composer.** Ctrl+Enter (Cmd+Enter on macOS) sends; Enter inserts a newline. The hint says so where sending is the point ("Ctrl+Enter sends. Your decisions save as you go.").
- **Disabled with reason.** Any disabled control renders its reason text beside it at all times (not on hover). The reason sentence is under 8 words and ends with a full stop.
- **Selects.** Changing the sort or a log filter re-renders in place; the count line updates ("2 of 9 match 'todo'").
- **Details.** Closed by default; state is not persisted.
- **Switches.** Flip immediately; the consequence sentence under the switch swaps on change; a section Save button becomes enabled only when a value differs from the saved one, with the reason "Nothing changed yet." until then and "Saved 14:10" after a save.
- **Theme.** Follow `prefers-color-scheme`; honour `data-theme="light|dark"` on the root when set by the host. No in-app theme toggle in phase 0.
- **Motion.** The only animations: the Working pin rotation (2.4s linear loop), button transitions (120ms), the details marker rotation (120ms), the switch knob (120ms). Under `prefers-reduced-motion: reduce` the pin stops; everything else is already instantaneous enough to keep.
- **Focus.** Every focusable element shows `outline: 2px solid var(--focus); outline-offset: 2px; border-radius: 6px` on `:focus-visible`. Inputs show a `--fg` border instead.
- **Keyboard.** Tab order follows DOM order, which is reading order: top bar, chat (strip, messages, dock, composer), right pane (tabs, view). Arrow keys move between radio cards in a `radiogroup`.

**C. Phone floor at 400×800:** the second assertion in B, plus `.tabs` must have `scrollWidth >= clientWidth` with `overflow-x: auto`.

**D. Pins:** every `.pin` has `data-pin` in the seven and `textContent.trim() === data-pin`.

**E. Colour literals:** a lint over all CSS except `tokens.css` must find zero `#[0-9a-f]{3,8}` and zero `rgba?(`. (Exception: the preview `.device` chrome, which imitates the built product and uses literal white and near-black.)

**F. Fonts loaded:** `document.fonts` contains Fraunces, Geist and JetBrains Mono after load; the page is laid out identically in the fallback stack (no layout dependence on font metrics).

**G. Contrast:** the twelve pairs in §11 at or above 4.5:1 after any token change.

**H. Visual parity:** screenshot each state at 1142×732 in light and dark and compare to `screens/<id>.html` rendered the same way. Differences must be explainable by real data, not by styling.

Manual checklist per screen: the next decision is visible without scrolling; the dock and composer never move when the chat scrolls; a locked tab shows its reason on hover; every disabled button shows its reason; no uppercase text except "Next step"; no mono text except code facts; no shadow larger than 2px except the thread glow.

## 14. Decisions log (what was decided and why)

| Decision | Replaces | Reason |
|---|---|---|
| Black-and-white glass islands on a monochrome ground | Monad parchment canvas | Requested: glassmorphism, black and white, floating islands |
| Coloured status words on tints | Monad's grayscale-only functional colour | Requested: label colours. Seven fixed states need to be scannable |
| Lake Blue kept for the one next-decision button only | A fully monochrome scheme | The "one thread" rule needs one colour that appears once; it is one token to change |
| Tabs carry the journey; the top-bar tape only remains as the Lane B request measure | Research Law 3 wanted both a tape and tabs | Cognitive load: the two indicators shared targets, so one was redundant |
| Geist for UI and body text; mono only for code facts | Monad's all-mono UI | Readability for non-technical founders; mono stayed where it signals a fact |
| Serif headings at 400 (Fraunces) | — | Kept from Monad; also Pramaan's incumbent display face |
| Sentence case everywhere; one 11px uppercase eyebrow | Uppercase buttons, tabs, labels | Cognitive load |
| Cards: gradient surface, inner highlight, 1px edge, 2px shadow | Flat cards; then floating 40px shadows | Requested: not skeuomorphic or floating, but not flat |
| Island and button shadows pulled to 2px; thread glow 14px | 40px island shadows, 16px button shadows | Same request |
| Chat anchored to the next-step card | Messages top-aligned with a 300px gap | Requested whitespace fix; keeps the decision and its context together |
| Project marks: 2×2 quarter-circle sigil, deterministic per name | Two random primitives | First attempt rejected as awful; the grid system gives coherence with variety |
| Selects with a custom chevron 12px from the edge, 38px controls | Native selects | Regression fix |
| Live logs as one compact line per row | Two-line rows with a stacked Details | Regression fix: screen left behind by the refactor |

## 16. Glossary

| Term | Meaning |
|---|---|
| Thread | The one next-decision control on a screen, the only element in `--thread` |
| Island | One of the three glass panes (top bar, chat, right pane) |

| Mark | The abstract 2×2 sigil that identifies a project card |
